# Lcloudy_AICraft

> 一套面向 AI 实践者的「轻量级能力演进工作区」—— 让提示词（Prompt）有家可归，让技能（Skill）有迹可循。

---

## 🎯 这是什么？

这是一个**用于系统化管理和迭代 AI 能力资产**的工作区模板。

你可以把它理解为：
- **一个文件即一个 AI 能力单元**（不是散落的 prompt 文件）
- **一条从 prompt → skill 的自然演进路径**（不是非此即彼）
- **一套可复用、可评估、可沉淀的技能标准**（不是一次性对话）

它不依赖任何平台或框架，纯 Markdown + 文件夹结构，开箱即用。

---

## 🧱 核心理念

```
┌─────────────────────────────────────────────────────────────┐
│  车间（场景），直接存放技能文件                             │
│  ├── {技能名}_prompt_vX.X.md   ← prompt 阶段：独立提示词   │
│  │        （升级后并入技能文件并删除）                     │
│  └── {技能名}_skill_vX.X.md    ← skill 阶段：四章合一      │
│            ├── 📥 加载说明    ← 入口与执行流程             │
│            ├── 🧭 工作指令    ← 角色/原则/裁决（Spec）     │
│            ├── ✅ 验收标准    ← 红线核验 + 风险披露        │
│            └── 📝 提示词模板  ← 可执行模式（Prompt）       │
└─────────────────────────────────────────────────────────────┘
```

**演化逻辑**：同一个技能，从一段可用的 `{技能名}_prompt_vX.X.md` 开始；成熟后用编写器一次性生成四章合一的 `{技能名}_skill_vX.X.md`，原 prompt 并入其中。**单个技能同一时间只有一个活跃文件。**

### 🔑 什么让 prompt 成为 skill？

两者都是 Markdown 文件，区别不在格式而在角色：**prompt 是「一次性输入」，skill 是「能力契约」**。判定看三条标准：

| 标准 | 含义 | 对应章节 |
| :--- | :--- | :--- |
| **可调用性** | 有固定入口，任何会话按名字即可加载 | 📥 加载说明 |
| **行为契约** | 行为边界与原则冲突裁决规则保持稳定 | 🧭 工作指令 |
| **可验收性** | 有可核验的红线检查与风险披露，输出可返工 | ✅ 验收标准 |

> **检验口径**：把这份文件交给一个全新会话的 AI，它能稳定产出同等质量的输出，就是 skill；否则还只是 prompt。
> **自包含**：技能文件全文粘贴进任何会话即可使用，不依赖读取外部文件——这让它天然跨平台、跨会话可移植。

## 📁 目录结构

```
Lcloudy_AICraft/
├── _config/                     # 全局制度
│   ├── changelog.md             # 版本变更日志
│   └── global_rules.md          # 全局命名/格式规范 + 判定标准
│
├── _prompts/                    # 全局编写器（用于生成技能文件）
│   ├── README.md                # 编写器使用手册
│   └── write_skill.md           # 单文件技能编写器
│
├── 文本处理车间/                 # 按场景划分的车间，直接存放技能文件
│   └── 结构化重塑_skill_v1.1.md  # 四章合一的完整技能（技能名在文件名中）
│
└── README.md                    # 本文件
```

> 📌 **车间内允许存在 `_TODO` 前缀文件作为个人研究笔记或待办清单（如 `摘要生成_TODO.md`），此类文件不计入正式技能资产，不要求配套 `prompt` 或 `skill` 文件。**

## 🚀 如何使用这个仓库？

### 场景一：我想用现成的技能

1. 找到对应车间的技能文件（如 `文本处理车间/结构化重塑_skill_v1.1.md`）
2. **复制全文**，粘贴进任意 AI 会话
3. 按「📥 加载说明」提供待处理的输入即可

### 场景二：我想把已有的 prompt 升级为 skill

1. 确保 prompt 文件已存在（如 `文本处理车间/摘要生成_prompt_v0.1.md`）
2. 按 `_prompts/write_skill.md` 的规则，提供：技能名称 + 一句话定位 + prompt 全文
3. 生成 `摘要生成_skill_v1.0.md` 后，删除原 `摘要生成_prompt_vX.X.md`（内容已并入）

> 详细规则见 `_prompts/README.md`

### 场景三：我想创建全新的技能

1. 在合适的车间下新建 `{技能名}_prompt_v0.1.md`，先跑起来、打磨提示词
2. 成熟后按场景二升级为 `{技能名}_skill_v1.0.md`
3. 在 `_config/changelog.md` 中记录本次新增

## 🧩 设计原则

| 原则 | 说明 |
| :--- | :--- |
| **场景优先** | 按业务场景而非技术类型组织内容 |
| **渐进演进** | prompt → skill，不急于一蹴而就 |
| **单文件自包含** | 一个技能 = 一个文件，粘贴即用，零外部依赖 |
| **格式统一** | 所有技能文件由同一编写器生成，文风结构一致 |
| **模块隔离** | 车间之间、技能之间互不依赖，可独立增删 |
| **人工可读** | 纯 Markdown，无需任何工具即可浏览和编辑 |
